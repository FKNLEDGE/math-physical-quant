# 进阶·编程深化 ① 用 C++ 给蒙特卡洛加速（pybind11）

> 你的工具栈是 **Python + 一点 C++**。这一课回答两个实际问题:**什么时候该上 C++?怎么上?**
> 答案可能和你想的相反——**C++ 不是"永远更快",而 NumPy 常常已经够用甚至更快**。
> 配套代码:[`cpp_speedup.py`](cpp_speedup.py) + [`mc_pricer.cpp`](mc_pricer.cpp)。

> 🧭 本质 → 三种写法 → 反直觉的实测 → 何时该上C++ → pybind11 怎么用 → 闭环。

---

## 一、本质（一句话）

> **先把代码写对、用 NumPy 向量化;只有当问题"难以向量化"时(路径依赖、提前退出、逐路径分支),才把那一小段热点搬到 C++。** 过早写 C++,常常是白费力气——因为 NumPy 本身就是在调用 C。

---

## 二、同一个蒙特卡洛,三种写法

给 [B4 蒙特卡洛期权定价](../../路线B-衍生品定价/04-蒙特卡洛定价/笔记.md) 提速,三种写法:

| 写法 | 长相 | 适合 |
|---|---|---|
| **纯 Python 循环** | `for i in range(n): ...` | 直观,但慢——解释器逐元素开销大 |
| **NumPy 向量化** | 一次生成所有路径的数组 | "Pythonic",**本身在调 C/SIMD**,可向量化的问题首选 |
| **C++ + pybind11** | 把内层循环写成 C++ 编译 | **难向量化**的问题(逐路径逻辑、提前退出) |

先**验证三者都算对**(实验①):都收敛到 Black-Scholes 解析解 9.413(蒙特卡洛误差 ~ 1/√N)。**先证明"快"不是靠算错。**

---

## 三、反直觉的实测结果 ⭐

### 欧式期权(可以向量化)→ NumPy 已经追平甚至超过朴素 C++

实验②(n=200,000):

| 方法 | 耗时 |
|---|---|
| 纯 Python | ~198 ms |
| **NumPy** | **6.1 ms** |
| C++ pybind11 | 8.0 ms |

> **看清楚:NumPy(6.1ms)比我手写的朴素 C++(8.0ms)还快!** 纯 Python 慢 32 倍,但 NumPy 和 C++ 旗鼓相当。
> 为什么?**NumPy 的向量化操作底层就是优化过的 C/SIMD 代码**——你用 `np.exp(array)` 时,已经在跑机器码了。我那个逐元素 `std::exp` 的 C++ 标量循环,并不比它快。

实验③:NumPy 和 C++ 相对纯 Python 都是**几十倍**加速、且**彼此相当**。结论:**能向量化时,先向量化——这是性价比之王,朴素 C++ 白忙。**

### 障碍期权(难向量化)→ C++ 才真正赢

实验④:向下敲出障碍期权(B=98 贴近现价,steps=250),**大量路径很早就敲出**:

| 方法 | 耗时 |
|---|---|
| NumPy(必须算完所有路径所有步) | 362 ms |
| **C++(敲出路径立刻退出)** | **161 ms** → 快 **2.3×** |

> **这才是 C++ 该上场的地方。** 障碍期权是**路径依赖 + 提前退出**:一旦某条路径跌破障碍,它就作废,后面的步不用算了。
> - C++ 能对**每条路径独立地 `break`**,省下大量计算。
> - NumPy 是"整批"操作,**无法对单条路径提前退出**——它必须把所有路径的所有步都算完(即使大部分早就死了)。
>
> 向量化的"整批"优势,在"逐路径提前退出"面前反而成了劣势。

## 四、何时该上 C++?(决策清单)

1. **先 profile**:用 `cProfile`/`%timeit` 找到真正的热点。**别凭感觉,要测量**(实验②就是在打脸"C++一定快"的直觉)。
2. **能向量化吗?** 能 → 用 NumPy,通常就够了(可向量化问题 NumPy ≈ C++)。
3. **难向量化吗?**(逐路径分支、提前退出、递归、复杂状态机)→ 这才是 C++ 的主场(实验④)。
4. **内存爆了吗?** NumPy 要把 N 条路径全开成数组(O(N) 内存);C++ 可以**流式**逐路径处理(O(1) 内存)。N 极大时 C++ 不爆内存。
5. **只搬热点**:把那一小段内层循环搬到 C++,用 pybind11 暴露给 Python,**其余照旧用 Python**——两全其美。

> 📌 **Knuth 名言**:"过早优化是万恶之源。" **先写对、再测量、最后只优化热点。**

---

## 五、pybind11 怎么用(三步)

1. **写 C++**:普通函数 + 一个 `PYBIND11_MODULE` 宏暴露它([`mc_pricer.cpp`](mc_pricer.cpp))。
2. **编译**:`g++ -O3 -shared -std=c++17 -fPIC $(python -m pybind11 --includes) mc_pricer.cpp -o mc_cpp$(python3-config --extension-suffix)`(代码里 `build_cpp()` 自动做)。
3. **import 即用**:`import mc_cpp; mc_cpp.european_call(...)`——和普通 Python 函数一样调用。

> pybind11 是 header-only(只要头文件),把 C++ 类型和 Python 类型自动来回转换。这是现代 "Python 调 C++" 最舒服的方式。

---

## 六、思维模型

1. **测量,别猜**:性能直觉经常错(谁能想到 NumPy 比手写 C++ 还快?)。**Profile first.**
2. **抽象层也是性能**:NumPy 不是"慢的 Python",它是"披着 Python 皮的 C"。**用对抽象,等于免费拿到 C 的速度。**
3. **向量化 vs 逐元素逻辑**:整批操作快,但**牺牲了"对单元素提前退出/分支"的灵活**。问题的结构决定哪种赢。
4. **只优化热点(帕累托)**:80% 的时间花在 20% 的代码上。**把 C++ 用在刀刃上**,别全盘重写。
5. **正确性 > 速度**:先用慢而对的版本(纯Python)当"标准答案",优化版必须和它对齐(实验①)。

---

## 七、哲学指导

> **工具的选择,本身是一种第一性原理思考:不是"哪个语言强",而是"这个具体问题的结构,适合哪种计算模式"。** 可向量化的问题适合 NumPy 的"整批";逐路径提前退出的问题适合 C++ 的"逐条灵活"。**没有最快的语言,只有最配问题的工具。**

这也呼应全项目的[「模型/工具是地图」](../../../docs/12-总复习知识地图.md):C++ 不是更高级的"疆域",它只是在某类问题上更合适的地图。**盲目上 C++ 显得专业,实则常常是过早优化的自欺**——和量化里"用花哨模型自欺"是同一种病。**诚实地测量,诚实地选工具。**

## 八、动手

跑 `python cpp_speedup.py`(首次自动编译),然后:

1. **改障碍位置**:把 `B` 从 98 改到 90(远离现价,很少敲出),看 C++ 对 NumPy 的优势是不是消失——**早退出救不了"没人早退出"的情形**。
2. **改 steps**:把障碍的 `steps` 调大(路径更长),看 C++ 优势怎么变。
3. **写你自己的 C++ 函数**:在 `mc_pricer.cpp` 里加一个**亚式期权**(算路径均值)的定价,绑定后从 Python 调——亲手走一遍 pybind11 流程。
4. **profile**:用 `python -m cProfile` 跑你某个慢脚本,找到真正的热点,再决定要不要上 C++。

## 九、本课小结（费曼版）

- **C++ 不是永远更快**:欧式期权(可向量化)上,**NumPy(6ms)甚至比朴素 C++(8ms)还快**——因为 NumPy 本身就是优化过的 C;纯 Python(198ms)慢几十倍。
- **C++ 的真正主场 = 难向量化**:障碍期权(路径依赖+提前退出),C++ 能让敲出路径立刻 `break`,比 NumPy 快 **2.3×**;NumPy 必须把所有路径所有步算完。
- **决策清单**:先 profile → 能向量化就用 NumPy → 难向量化(逐路径/提前退出/省内存)才上 C++ → 只搬热点。
- **pybind11 三步**:写 C++ + `PYBIND11_MODULE` → g++ 编译成 .so → `import` 即用。
- **心法**:测量别猜;过早优化是万恶之源;没有最快的语言,只有最配问题的工具。
